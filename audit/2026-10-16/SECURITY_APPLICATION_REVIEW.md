# SpacePilot Security and Application Review

Audited revision: [`943a196a12a879a0ca2d9b9e97985fe33b3a5697`](https://github.com/jaysonguglietta/spacepilot/commit/943a196a12a879a0ca2d9b9e97985fe33b3a5697) on `main`, reconfirmed October 18, 2026. Review covers both desktop apps, services, tests, packaging, workflows and product behavior. [The detailed application feature review](APPLICATION_FEATURE_REVIEW.md) contains the full claimed-versus-implemented matrix and fourteen product defects. [Source inventory](source-inventory.txt), [verification results](source-verification.json), [GitHub evidence](github-evidence.json), and [macOS reproduction](mac-quarantine-proof.txt) preserve the review basis.

## 1. Executive Summary

**Do not ship the current release as a safety-first cleanup product without correcting the high-priority data-loss paths.** Windows Firefox “History” removes a database that also contains bookmarks. Windows protection checks only a selected directory’s own path, so protected files inside it can be moved or permanently deleted. Windows buttons labeled “Quarantine selected” can permanently delete personal files when a global preference is off. Both apps trust scanned paths and quarantine metadata too far into destructive operations; the macOS versions of three such failures were reproduced against unchanged production services using isolated temporary fixtures.

There is no application server, remote API, login system or tenant model in this revision. I found no evidence of unauthenticated remote code execution, authentication bypass, cross-tenant access, SSRF, web XSS, SQL/NoSQL injection, unsafe object deserialization or committed credential material. The realistic adversaries are local processes able to change writable files between review and action, lower-privilege actors planting state before an elevated Windows launch, compromised package sources or release infrastructure, and normal users relying on inaccurate safety labels. Same-user manifest tampering is **not automatically privilege escalation**: damage is bounded by the app process’s access unless the app has extra elevation or macOS TCC access.

Severity here measures user-file integrity, recoverability and release compromise as well as attacker reach. **High** includes reproducible or deterministic user-data safety violations even when the trigger is a normal UI action. The macOS proof uses compiled services and synthetic files; Windows findings are source-confirmed but require Windows integration testing. The current revision’s [Windows CI](https://github.com/jaysonguglietta/spacepilot/actions/runs/28025676401) and [macOS CI](https://github.com/jaysonguglietta/spacepilot/actions/runs/28025676314) passed. A CI pass does not cover the adversarial cases below.

## 2. System Overview and Trust Boundaries

Windows is a WPF application targeting .NET 8; `MainViewModel` orchestrates filesystem, package-manager, registry, Task Scheduler and restore-point services. The manifest requests `asInvoker`, but users can run it elevated and the settings audit recognizes administrator mode. macOS is a SwiftUI/Swift Package Manager executable with `MacAppState` delegating scans, quarantine, receipts and OS diagnostics to local services. Both persist JSON preferences, quarantine manifests and receipts in per-user app data and keep activity largely in memory. Windows can call WinGet, PowerShell and `schtasks`; macOS calls fixed local diagnostic tools. Neither app implements a listener or cloud backend.

| Boundary | Lower-trust input | Higher-impact action or asset |
| --- | --- | --- |
| Filesystem scan → cleanup | Temp/cache/browser/personal paths, symlinks, file contents, races | Move, recursive delete, purge of the app’s accessible files |
| JSON manifest → recovery | Mutable per-user IDs, payload and original paths, dates | Restore destination and recursive purge target |
| User preference → workflow | Confirmation, quarantine, protection and retention settings | Which files are touched, reversibility, notice and expiry |
| OS tool output → UI | WinGet, process, scheduler and memory output | Update decisions, availability, health recommendations |
| Local package list → WinGet | User-selected JSON and configured package sources | Package installation and updates, potentially with UAC |
| Repository/CI → release | Workflow inputs, mutable third-party actions, build dependencies | Published binaries and optional signing credentials |

Valuable assets are personal files and browser profile data, recoverable quarantine payloads plus metadata, accurate receipts, protected-path policy, package-install authority, code-signing material when configured, and trustworthy releases. The OS account supplies the actual access-control boundary. A checksum or same-user encryption of a manifest would not turn it into a trusted instruction source for an elevated process.

## 3. Threat Model

1. **Malicious same-user process or untrusted app:** creates symlinks/junctions in cleanup roots, changes a scanned file, edits a writable manifest, or fills folders with files and process output. It seeks mistaken deletion, movement of more sensitive files, corrupt recovery or denial of service. Under ordinary same-user execution, this often overlaps the attacker’s existing rights; the product’s safety guarantee and any extra app access remain the relevant boundary.
2. **Lower-privilege local actor before a privileged run:** plants a manifest entry or executable in a searched writable directory, then waits for SpacePilot to run as administrator. Elevated exploitation depends on actual ACLs, launch directory and Windows integrity level; those conditions were not reproduced here.
3. **Compromised package source, release account or workflow dependency:** supplies a hostile package or build step, intercepts mutable third-party action references, or publishes unsigned assets through a release job. There is no evidence that this has occurred; the repo lacks several preventive gates.
4. **Legitimate user acting on misleading UI:** selects “History,” “Quarantine selected,” recommended duplicates or an apparently protected directory and gets a broader or less reversible action than expected. This path is currently more direct than a remote exploit.
5. **Availability attacker or unusually large local dataset:** causes blocking helper output, unbounded enumeration/hashing or corrupt numeric preferences. The effect is local app unavailability, not service-wide network DoS.

Likely chains are scan → rename ancestor to link → approved path check → move outside file; forged manifest → startup retention/purge → recursive deletion; and supported elevated launch → writable helper-search directory → unwanted program execution. Each chain’s exact prerequisites are stated with its finding.

## 5. Prioritized Findings

All code references below refer to the audited commit. “Confirmed” means source flow is established; only findings explicitly marked reproduced were exercised against compiled services. Each scenario states the required attacker or user action.

### SP-01 — Firefox History removes bookmarks database

**Severity: High. Confidence: High for database removal; Medium for permanent loss after Firefox recovery. Status: confirmed static finding.**

**Affected/evidence:** Windows `ViewModels/MainViewModel.cs:1728–1733` returns `places.sqlite` for the Firefox History checkbox, and `:1630–1667` sends that whole file through cleanup. [Mozilla documents](https://support.mozilla.org/en-US/kb/profiles-where-firefox-stores-user-data) that `places.sqlite` stores bookmarks, downloads and browsing history. `Services/QuarantineService.cs:130–133` refuses restore when Firefox has recreated the original path.

**Scenario/impact:** A user selects only History and confirms. The database containing bookmarks is moved or deleted, even though the action is presented as history-only; subsequent Firefox startup can create a replacement and complicate restore. Backups or sync may save some data, so permanent loss on every profile is **not** asserted. **Fix/patch:** disable Firefox History mutation immediately and hand users to Firefox’s native Clear History UI. Any future selective handler must preserve bookmark/download records, account for SQLite WAL/SHM and Firefox version, and use a supported transaction/backup approach. **Validation:** synthetic Firefox profile with bookmarks, visits, downloads and active WAL; after a history-only action, bookmarks survive, intended visits are gone, Firefox opens normally, and conflict recovery works. **CWE:** CWE-840 (business-logic error), CWE-73 where a broad file target substitutes for a narrower action.

### SP-02 — Protected descendants are swept up by Windows directory cleanup

**Severity: High. Confidence: High for the source path; Windows runtime pending. Status: confirmed static finding.**

**Affected/evidence:** `Services/ProtectionPolicyService.cs:15–19,48–53` evaluates only the supplied path. `ViewModels/MainViewModel.cs:783–788` checks the top-level candidate; `Services/CleanerService.cs:146–174` admits old directory candidates and `:63–69` recursively deletes them; `Services/QuarantineService.cs:84–86` moves the whole directory. The default protection list includes document extensions in `Models/UserPreferences.cs`.

**Scenario/impact:** An old `%TEMP%\cache` directory contains `keep.pdf` or a custom protected child. The parent is allowed because its own path is unprotected, so selection can move the document and, with permanent mode or later purge, delete it. A normal user can hit this without an attacker. **Fix/patch:** enforce protection inside the mutation service; reject any whole-directory operation containing protected descendants, or generate leaf operations that preserve protected children. Recalculate scope and bytes immediately before action. **Validation:** nested protected file/path fixtures, both cleanup modes, newly added protected child after preview, mixed allowed/protected children. Nothing protected may move or be deleted. **CWE:** CWE-863 (incorrect authorization), CWE-693 (protection mechanism failure) within the product policy.

### SP-03 — Windows “Quarantine selected” can permanently delete personal files

**Severity: High. Confidence: High for reachable configuration; Windows runtime pending. Status: confirmed static finding.**

**Affected/evidence:** `MainWindow.xaml:562–565,586–589` labels manual large-file and duplicate buttons as quarantine actions. `ViewModels/MainViewModel.cs:1035–1074` routes them through `RunCandidateCleanupAsync`; `:813–827` omits confirmation when `ConfirmBeforeCleanup=false`; `:829–879` calls permanent `CleanerService.CleanAsync` when global `UseQuarantine=false`.

**Scenario/impact:** A user disables quarantine for routine temp files, then clicks “Quarantine selected” for a personal file. The selected file is permanently deleted; if confirmations are also off, there is no final action-specific warning. **Fix/patch:** use a typed, explicit operation mode; force quarantine for manual personal-file actions, with a mandatory final review independent of generic temp-cleaner settings. If irreversible personal deletion is an intended feature, label it and require a separate hard-to-miss irreversible confirmation. **Validation:** the 2×2 preference matrix for both manual flows; every button labeled quarantine must leave a manifest/payload and be restorable, and no silent permanent path may remain. **CWE:** CWE-841 (improper enforcement of workflow), CWE-840.

### SP-04 — Persisted manifest paths can direct purge or restore outside quarantine

**Severity: Medium normally; potentially High when higher-integrity execution consumes lower-trust state. Confidence: High. Status: reproduced on macOS; Windows source-confirmed.**

**Affected/evidence:** macOS `Services.swift:336–345` decodes absolute `payloadPath` and `originalPath`; `:290–325` uses them directly and purges the payload’s parent. Windows `Services/QuarantineService.cs:219–240` deserializes equivalent fields; `:297–303` recursively deletes `GetParent(entry.PayloadPath)`. Windows startup runs expired-entry purge at `ViewModels/MainViewModel.cs:678–686`, without requiring the payload to be inside quarantine. The isolated [macOS proof](mac-quarantine-proof.txt) shows `forged_manifest_deleted_unrelated_parent=true; warnings=0`.

**Scenario/impact:** A local process that can edit the manifest forges a plausible entry whose payload path is an existing file within an unrelated directory. Mac UI purge deletes that parent after selection; on Windows, an expired forged entry can be purged on launch. Restore can also move data to a serialized destination. Same-user access limits impact unless the app has extra privileges. **Fix/patch:** validate opaque IDs and derive `quarantineRoot/<id>/payload` internally; reject forged absolute paths, traversal, root/sibling paths, links, type mismatches and duplicate IDs. Separate elevated mutations from user-writable metadata; use handle-relative, no-follow operations where available. A checksum alongside writable JSON is insufficient. **Validation:** forged outside parent, nonexistent payload, root path, `..`, symlink/junction ancestor and tampered original destination; every outside sentinel survives purge and restore, including auto-expiry. **CWE:** CWE-73, CWE-22; conditional CWE-250.

### SP-05 — Scan-time path approval can be bypassed before cleanup

**Severity: Medium normally; additional privilege impact is conditional. Confidence: High on macOS, Medium on Windows-specific races. Status: reproduced on macOS; Windows source-confirmed.**

**Affected/evidence:** macOS `Services.swift:24–45` and Windows `Services/PathSafety.cs:14–28` check lexical path prefixes. Initial scanners skip links they see, but macOS `Services.swift:249–267` and Windows `Services/CleanerService.cs:43–69`, `Services/QuarantineService.cs:57–86` mutate later using path strings without verifying root/ancestor identity. Windows `Services/CleanerService.cs:184–245` accepts existing roots that could be junctions. The [macOS fixture](mac-quarantine-proof.txt) replaced a scanned ancestor with a symlink and recorded `outside_file_moved=true`; the [extended fixture](mac-extended-proof.txt) also replaced a scanned file with a directory containing a protected PDF. The current default macOS rules do not select directories, so the modeled directory-candidate descendant example in that proof demonstrates a latent service-contract gap, not a default-rule reachability claim.

**Scenario/impact:** A writable cache subdirectory is renamed after scan and replaced with a link to a personal directory; the user approves the original filename, while the move resolves to another physical file. A concurrent local writer or an ordinary app update can cause stale identities. **Fix/patch:** bind preview to a stable root, device/file ID and type; at mutation, reject changed ancestors or candidates, recalculate protection/age and operate through no-follow directory/handle-relative APIs. Canonicalize as a useful preliminary check, but do not rely on a second text-path check to close a race. **Validation:** symlink/junction root and ancestor swaps, file-to-directory replacement, protected alias, changed inode/type, and normal concurrent writes; prompt for rescan and preserve outside sentinels. **CWE:** CWE-367, CWE-61/CWE-59, CWE-22.

### SP-06 — Quarantine moves are not durably tied to recovery records

**Severity: Medium. Confidence: High. Status: macOS manifest-write failure reproduced; Windows source-confirmed.**

**Affected/evidence:** macOS `Services.swift:267–287,336–345` moves payloads, then suppresses manifest write errors with `try?`; `loadManifest` turns corrupt/missing state into `[]`. Windows `Services/QuarantineService.cs:75–111` moves multiple payloads before a single `File.WriteAllText` at `:240`; cancellation/crash between those steps leaves payloads without entries, and malformed JSON is mapped to empty at `:231–233`. The [macOS proof](mac-quarantine-proof.txt) returned one successful entry, zero warnings and zero visible recovery entries after an injected manifest-path failure.

**Scenario/impact:** Disk full, denied write, crash, corrupt JSON or overlapping instances leave moved files physically in quarantine but absent from Recovery. Later saves can overwrite surviving metadata. Windows cross-volume directory fallback at `QuarantineService.cs:257–295` also skips reparse-point children then deletes the source; this loses the **link objects**, not their external targets. **Fix/patch:** durable per-entry intent/completed journal, atomic write plus fsync, cross-process lock or single-instance enforcement, crash reconciliation and an orphan-recovery UI. For cross-volume moves, verify a complete object inventory before deleting the source; reject unsupported link types rather than silently dropping them. Return success only when durable recovery is established. **Validation:** injected write failure, cancellation after first move, crash at each step, corrupt manifest, concurrent instances, cross-volume symlink/junction fixture and restore; every moved object is recorded or safely rolled back. **CWE:** CWE-252, CWE-703, CWE-459.

### SP-07 — Duplicate decisions become stale and personal files are preselected

**Severity: Medium. Confidence: High; stale-content behavior reproduced on macOS. Status: confirmed.**

**Affected/evidence:** Windows `Services/StorageAnalysisService.cs:169–187` and `ViewModels/DuplicateFileViewModel.cs:10–14`; macOS `Services.swift:514–533` and `MacAppState.swift:234–262` hash duplicates, mark all but one recommended, and preselect those rows. Neither manual action rechecks hash, file ID or keeper before `CleanerService`/`QuarantineService`. In a temporary fixture, a selected duplicate was changed to unique content after hashing and still quarantined without warning.

**Scenario/impact:** A user sees two equal files, the app chooses one based on timestamp/path rather than the user’s need for both locations, and the user confirms a preselected batch. A background edit can make the selected file unique; the user can also select every copy. Later purge or Windows permanent mode may remove the last surviving content. **Fix/patch:** start with zero personal files selected; show groups and explicit keeper choice, prohibit cleanup of every verified copy, and rehash/verify selected and keeper files using stable IDs immediately before mutation. **Validation:** no default duplicate selection; keeper cannot join an all-copies deletion; mutate a selected file between scan and action and require a rescan warning; confirm no document moves without a direct per-item choice. **CWE:** CWE-841/CWE-840 (workflow and integrity logic).

### SP-08 — WinGet update discovery reports failure as “no updates”

**Severity: Medium for security-patch visibility and feature correctness. Confidence: High for API mismatch; Windows runtime pending. Status: confirmed static finding.**

**Affected/evidence:** `Services/WingetService.cs:19–25` calls `winget upgrade --accept-source-agreements --output json` and maps every unsuccessful result to an empty package list. [Microsoft’s upgrade options](https://learn.microsoft.com/en-us/windows/package-manager/winget/upgrade) and [current command argument source](https://raw.githubusercontent.com/microsoft/winget-cli/master/src/AppInstallerCLICore/Commands/UpgradeCommand.cpp) contain no `--output json` option. `ViewModels/MainViewModel.cs:1245–1247` presents empty as “No WinGet updates were found.” The fallback table parser is not reached when the command fails.

**Scenario/impact:** An unsupported option, missing WinGet, source error or network failure all appear to the user as a fully updated system; package security updates may be missed. No malicious package source is needed. **Fix/patch:** use a supported structured WinGet interface such as `Microsoft.Management.Deployment`, or a version-aware CLI adapter. Return an explicit `Success(items) | Unavailable(reason) | Failed(reason)` result. If table parsing remains, use column boundaries, locale tests and robust multiword-name parsing; `WingetService.cs:251–263` currently splits names on spaces. **Validation:** real supported WinGet builds, unknown flag, absent executable, offline source, Unicode/multiword names, warning/footer output and true empty success. **CWE:** CWE-391 (unchecked error condition), CWE-754 (improper check for unusual conditions).

### SP-09 — Windows helper search can run a planted executable

**Severity: Medium conditional; potentially High if an elevated launch searches an attacker-writable directory. Confidence: High for source/search behavior, Medium for deployment preconditions. Status: source-confirmed, local attack not reproduced.**

**Affected/evidence:** `Services/StartupService.cs:108–116`, `ScheduledScanService.cs:69–77` and `WingetService.cs:80–88` pass bare `schtasks.exe`/`winget.exe` to `ProcessStartInfo`. Startup inventory runs during initialization at `ViewModels/MainViewModel.cs:690`. [Microsoft documents the executable search order](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw); its impact here depends on the app/current directory and executable ACLs. PowerShell has a bare-name fallback in `Services/SystemRestoreService.cs:21–23`.

**Scenario/impact:** A local actor able to plant `schtasks.exe` in a directory searched before System32 waits for SpacePilot to start. The actor’s executable runs with SpacePilot’s token, possibly elevated. Under same-user standard execution there may be no privilege gain, but startup inventory creates a predictable trigger. **Fix/patch:** resolve system tools to trusted absolute system-directory paths using OS APIs; resolve WinGet’s approved installation/package identity rather than arbitrary PATH; remove bare PowerShell fallback and launch with a trusted working directory. Use `ArgumentList` for arguments as separate hardening. **Validation:** inert fake helper in temporary current/application/PATH directories; it must never run in standard, portable and elevated test configurations. **CWE:** CWE-426/CWE-427.

### SP-10 — Helper output can indefinitely block core workflows

**Severity: Low security, Medium availability. Confidence: High for deadlock pattern; macOS pattern reproduced. Status: confirmed.**

**Affected/evidence:** macOS `Services.swift:858–870` waits for a child to exit before draining its stdout and never drains stderr. Windows `Services/ScheduledScanService.cs:83–85`, `StartupService.cs:122–123`, `SystemRestoreService.cs:77–79` and `WingetService.cs:95–106` read streams synchronously before timeout/cancellation can complete. macOS runs its performance sample at startup. A controlled 2 MiB `/bin/cat` fixture using the same macOS wait-before-drain pattern stayed blocked until a three-second watchdog terminated the isolated process group ([proof](mac-extended-proof.txt)); [Microsoft also documents](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.redirectstandardoutput?view=net-8.0) the redirected-output deadlock class.

**Scenario/impact:** A verbose or hung helper, long local process list or malformed package source holds a pipe open, keeping app `IsBusy` active and cleanup/recovery controls unavailable. This is not an inbound network DoS. **Fix/patch:** read stdout/stderr concurrently with byte caps, enforce a deadline over process execution *and* reads, terminate the process tree on timeout/cancel, inspect exit status and surface an actionable error. **Validation:** synthetic helper floods both pipes, never exits, prompts for input and spawns a child; the UI returns to idle within the deadline without losing completed mutations. **CWE:** CWE-400/CWE-833.

### SP-11 — Release workflow permits unreviewed, unsigned builds

**Severity: Medium release-integrity gap. Confidence: High for repository/workflow state; no compromise asserted. Status: confirmed configuration gap.**

**Affected/evidence:** `.github/workflows/release.yml:24–25` gives workflow-wide `contents: write`; `:89–107` explicitly falls back to unsigned Windows artifacts when signing secrets are absent; macOS `scripts/macos/build-app.sh:34–35` applies only ad-hoc signing, and no notarization step exists. The workflow publishes assets at `.github/workflows/release.yml:215–236`. GitHub’s API reports `main` `protected:false` and no repository rulesets as of October 18, 2026 ([captured metadata](github-evidence.json)). The workflows reference `actions/checkout@v4`, `actions/setup-dotnet@v4` and other mutable tags. GitHub [recommends pinning actions to full commit SHAs](https://docs.github.com/en/actions/reference/security/secure-use).

**Scenario/impact:** An authorized but compromised release account, mutable third-party action, or accidentally unsigned manual release can publish assets carrying the project name without a required signature/notarization gate. Checksums uploaded beside the artifact by the same job do not provide independent authenticity. A public [v0.1.0 release](https://github.com/jaysonguglietta/spacepilot/releases/tag/v0.1.0) exists; its binary signatures were **not** downloaded or verified, so this finding does not assert those particular assets are malicious or unsigned. **Fix/patch:** require protected main/tags, review and passing status checks; put signing in a restricted release environment with required reviewers; fail release if signatures/notarization/verification are missing; pin all actions to vetted SHAs; scope `contents:write` to only the publish job. Restrict signing secrets from PR CI (`windows-ci.yml:16–17,47–54` currently makes them available to same-repository PR runs when configured; fork PRs normally receive no such secrets). **Validation:** unsigned/ad-hoc-only release job must fail, a signed test release must pass `Get-AuthenticodeSignature`, `codesign`, `spctl`/notarization checks, and branch/ruleset API must show enforced review/status policies. **CWE:** CWE-494 (untrusted code download), CWE-829 (untrusted functionality), as defense-in-depth categories.

### SP-12 — Release version input is interpolated into a shell script

**Severity: Low in the current permission model. Confidence: High for script interpretation. Status: locally reproduced with a harmless marker.**

**Affected/evidence:** `.github/workflows/release.yml:45–49,125–133,183–195` places `${{ inputs.version }}` inside quoted PowerShell/Bash `run:` scripts before the shell parses them. The [local probe](ci-input-proof.txt) demonstrates Bash executing the fixed `$(printf audit-code-executed)` marker within the interpolated version string. [GitHub explains](https://docs.github.com/en/actions/concepts/security/script-injections) that expression substitution inside a generated shell script can execute untrusted input.

**Scenario/impact:** A workflow dispatcher with permission to supply `version` can run shell code in the packaging/publish job and potentially use that job’s token. This is **not** an unauthenticated public entry point; repository workflow-dispatch permission is required, and a maintainer may already have comparable code authority. **Fix/patch:** pass input via a step `env:` value, read it as data, and allowlist release versions such as `^[0-9]+\.[0-9]+\.[0-9]+(?:-[A-Za-z0-9.-]+)?$` before using it in paths/tags. Never embed the raw expression in script text. **Validation:** harmless metacharacter input must be rejected before packaging; ordinary semver passes; Windows and Bash steps preserve the literal value without execution. **CWE:** CWE-78 with limited reachability.

### SP-13 — File/process volume and numeric settings can exhaust or crash the app

**Severity: Low security, Medium robustness for a desktop cleanup tool. Confidence: High for code behavior; local resource attack not stress-tested. Status: confirmed bounded-scope gap.**

**Affected/evidence:** macOS `Services.swift:426–470,476–577` enumerates all storage files and may hash all equal-size groups before applying output caps; Windows `Services/StorageAnalysisService.cs:130–199` collects all candidates before group limits. Neither has a work/byte/time budget inside hash loops. macOS `Services.swift:428,478` multiplies an unvalidated `Int` threshold by 1,048,576; `Views.swift:294,347` directly binds an integer field and preferences decode at `Services.swift:403–409` has no service-boundary range check. A checked fixture confirmed overflow for `Int.max` without intentionally crashing the app.

**Scenario/impact:** A huge or growing local tree can consume sustained CPU, disk I/O and memory; an extreme but representable threshold can trap and terminate the macOS process. No remote service is exposed. **Fix/patch:** bound files/bytes/elapsed time and warning counts, support cancellation/progress, avoid keeping all paths in memory, and validate all persisted/input thresholds before multiplication using overflow-safe operations. **Validation:** synthetic huge/sparse/growing trees, cancellation midway, corrupt preferences, max integer, inaccessible/remote mount fixtures; show partial status and return to idle within budget. **CWE:** CWE-400/CWE-190.

## 6. Exploitation Chains and Combined-Risk Scenarios

**Safety-promise bypass:** A Windows user selects an old temp-directory candidate with a protected document inside. The view model checks only the parent, then permanent mode recursively deletes it. The same user may have previously disabled confirmations; no malware is needed. A parallel macOS path uses a post-scan ancestor-link swap to turn an approved cache-file selection into movement of a different outside file. These are distinct implementations of a scan/action trust gap.

**Recovery failure:** A selected personal file is preselected as a duplicate and moved to quarantine. Manifest persistence fails or the process crashes. Recovery shows no entry; Windows automatic retention could later purge a recorded payload, while an unrecorded payload can become an opaque orphan. The bytes may still be physically present until a later deletion; the confirmed failure is loss of normal recovery and misleading success.

**Conditional elevated local attack:** A lower-privilege actor must be able to edit the specific Windows profile manifest or plant a helper in the app’s executable search path. If a user subsequently runs SpacePilot elevated, manifest-driven purge or helper execution can occur with elevated rights. Exact ACLs, integrity level and current-directory placement must be tested on the intended install type before calling this a demonstrated privilege escalation.

**Supply chain:** An actor with release-workflow authority could dispatch a version containing shell syntax; if signing secrets are configured in the job, they may be exposed. Existing repository permissions may already give that actor code execution, so the injection is a defense gap rather than a claimed public RCE. A separate compromised action or release account could publish artifacts unless signing and review gates are enforced.

## 7. Dependency and Configuration Risks

- The Windows app project has no direct third-party `PackageReference`; the test project references Microsoft.NET.Test.Sdk 17.11.1, xUnit 2.9.2, xunit.runner.visualstudio 2.8.2 and coverlet.collector 6.0.2. The macOS `Package.swift` declares no external packages. WiX CLI is installed at version 6.0.2 in CI. No locked transitive dependency inventory, NuGet audit output, SBOM or binary composition attestation was reviewed; therefore **no clean-CVE claim** is made.
- Windows targets .NET 8 and publishes a framework-dependent default package. [Microsoft states .NET 8 support ends November 10, 2026](https://devblogs.microsoft.com/dotnet/dotnet-8-9-end-of-support/). This is a near-term maintenance requirement as of the October 18 review, not a claim that .NET 8 is already unsupported. Retarget to supported .NET 10 after regression testing and document runtime servicing for existing installations.
- The macOS app bundle’s `Info.plist` hardcodes version `0.1.0` while the release workflow can name a DMG/ZIP with a different `RELEASE_VERSION`; `scripts/macos/build-app.sh` only ad-hoc signs. Fix version injection and enforce Developer ID/hardened runtime/notarization before public distribution.
- `main` is unprotected and no repository rulesets were returned by the GitHub API. The audited commit itself is unsigned. Tag protection, organization policy and environment-gate settings were not independently verified. CI builds/tests pass at the audited SHA, but tests omit malicious manifests, root junctions, protected nested content, cross-volume copy, Firefox history semantics and several end-to-end UI states.
- Windows’ normal app manifest uses `asInvoker`, an existing least-privilege control. macOS has no entitlement/sandbox declaration in the reviewed package/build scripts. Whether TCC grants extra access to the distributed app, and whether app-data ACLs restrict other local users, require inspection on an installed build. Plaintext quarantine can retain cookies, session tokens, browser data and crash dumps; clarify that “cleanup” does not erase them until purge.

## 8. Secure Design Gaps and Product Quality

The most important design change is to treat **file identity and recoverability** as the unit of a cleanup transaction. A preview should carry trusted rule/root provenance, stable file identity, exact intended type and a snapshot of relevant metadata. The mutation service should enforce those fields again, with protected descendants and no-follow ancestry. The quarantine journal should be durable before the original can disappear, recoverable after interruption, and inspectable by users. Receipt creation should share that transaction path on both platforms, including manual personal-file operations.

The product currently diverges from its own copy. macOS exposes confirmation, quarantine and retention controls without using them; it also omits receipts for large-file/duplicate actions. Windows labels manual actions as quarantine even when the global setting selects permanent deletion. Both apps preselect duplicate personal files. The [feature review](APPLICATION_FEATURE_REVIEW.md) records all fourteen defects, including double-counted macOS candidates, stale Windows Health reclaim plan, incomplete Windows storage map, false memory-health states, ignored busy actions, incomplete error/empty states and localized Task Scheduler parsing.

Accessibility foundations exist: WPF defines focus visuals and automation names, and SwiftUI uses native controls. The macOS icon-only selection buttons lack a contextual label and selected-state semantics; fix them as real toggles or explicit accessible controls. Windows grid selection announcements, text scaling, high-contrast colors and minimum-window clipping need actual Narrator/VoiceOver and desktop testing. The checked QA matrices describe expected tests, not recorded passes. Neither platform exposes user cancellation for long storage/duplicate scans. These are release-quality gaps, not invented web ARIA or mobile requirements.

No custom cryptographic weakness was found: duplicate comparison uses SHA-256. Hash equality at scan time does **not** authorize deleting a later, changed file. OS-native text binding reduces classic HTML/XSS exposure, and neither codebase exposes a template, LDAP, SQL or HTTP parser. Keep those categories outside the issue count unless new interfaces are added.

**Required adversarial regression suite:**

## 11. Open Questions and Assumptions

- **Elevated Windows deployment:** Is Run as administrator an intended regular workflow? Verify whether a lower-integrity process can edit the exact manifest/app directory consumed by that elevated instance and what working directory executable search uses. Severity amplification in SP-04/SP-09 depends on those facts.
- **Recovery/retention contract:** Should Windows retention silently purge on launch, require review, or merely recommend purging? Should macOS retention be advisory or active? Define per-entry expiry and the user’s guaranteed recovery window before implementing further automation.
- **Personal-file deletion:** Should the product *ever* allow irreversible cleanup of large/duplicate personal files? Current button labels promise quarantine. The safe default is quarantine with mandatory consent and explicit keeper choice.
- **Distribution policy:** Are signing certificates, repository environment approvals, organization branch/tag policies and clean-device QA available but configured outside this repository? The API checks establish only unprotected `main` and no repository rulesets.
- **Data protection:** What installed-build ACLs/permissions protect `LocalAppData` and `~/Library/Application Support/SpacePilot`, and what extra TCC grants can the signed Mac app receive? Verify on actual installations before claiming cross-user privacy or lower-to-higher privilege exploitation.
- **Feature semantics:** Is macOS intended to have the same protection editor, storage map, retention, receipt export and category filters as Windows, or should shared copy scope those as Windows-only? Define accurate scan completeness and RAM-pressure labels before expanding the UI.

The repository was reviewed at a fixed commit. A later commit, different package-source state or deployment configuration changes the conclusion; re-run the specific adversarial tests on the exact release candidate before public distribution.
